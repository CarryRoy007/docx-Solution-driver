# 写作质量规范

> Phase 5 内容撰写时的质量标准。所有输出的 Markdown 必须遵守。

## 基本要求

- 语言: 简体中文
- 风格: 专业、客观、逻辑清晰
- 禁止: emoji、网络用语、感叹句、主观判断
- 段落长度: 3-8句, 避免超长段落

## 结构规范

- 每节必须有引导段 (概述本节内容)
- 每节必须有小结段 (总结本节要点)
- 段落之间有逻辑衔接
- 并列关系用分号或 "首先/其次/最后" 等连接词

## 内容密度

- 避免空话套话 (如 "随着时代发展..." "在党的领导下...")
- 用数据说话, 尽量提供定量信息
- 技术描述要具体到模块/接口/协议层面
- 引用他人的观点/数据必须标注来源

## 去品牌化规则

当用户选择"摘抄但去品牌"策略时:

| 原文 | 替换为 |
|------|--------|
| 产品名称 (如 "XX云平台") | "本方案平台" / "该平台" |
| 型号/版本 (如 "v3.2.1") | 删除或改为通用描述 |
| 公司名称 | "我方" / "建设方" / "系统承建方" |
| 商标/品牌名称 | 通用技术术语 |
| Logo 图片 | 标记提醒用户替换 |

## 图表引用格式

```markdown
![架构示意图](03_diagrams/png/arch_01.png)
```

docx-formatter 会自动将 alt 文本作为图题, 格式化为 "图X: 架构示意图"。

## 常见问题

1. **过度引用**: 不要整段照搬素材, 用自己的语言重组
2. **信息缺失**: 不确定的数据不要编造, 标注 "待补充" 并告知用户
3. **技术深度不一致**: 面向决策层的方案可以适度简化技术描述; 面向技术评审的方案需要详细到接口/协议/配置层面
